## Q1: 一个任务要连多个数据库怎么办？ {#q1}

很常见，比如「对比 A 库和 B 库的客户表」。

做法：在 `1配置文件/` 下放两个 ini（每库一个），脚本里多次调用 `connect()`：

```python
from 工具.config_loader import connect

conn_a = connect("孝南-食堂")
conn_b = connect("为知V2-供应链")
```

每个连接独立管理事务。如果数据量很大，建议**先把两边数据分别落到 `输出数据/` 的临时 CSV，再用 pandas 做对比**，而不是在 Python 里边查边对比，更容易排查。

参考样例：`数据处理模板项目/食堂与供应链客户对比/对比食堂与供应链客户数据.py`。

## Q2: 项目里已经有自己的读配置函数了，还要用 `config_loader.py` 吗？ {#q2}

**不用强行替换。** 本模式关注的是**目录结构 + 工作流程**，不是某个具体函数。

如果项目里已经有 `load_db_config()` 或类似的：
- 继续用它
- 但请保持：ini 配置文件放在 `1配置文件/` 下，每个环境一个文件，命名遵循 `配置文件-<环境>-<库说明>.ini`

这样新成员看 `1配置文件/` 就能快速理解项目连接了哪些库。

## Q3: 我不是用 MySQL / pymysql，是 PostgreSQL / SQLite / Oracle，能用吗？ {#q3}

可以。`config_loader.py` 默认是 pymysql，但ini 配置本身与驱动无关。

适配方法：
- **PostgreSQL**：把 `connect()` 里的 `pymysql.connect` 换成 `psycopg2.connect`，参数几乎一样。
- **SQLite**：ini 里把 `host/port` 省略，加一个 `file = ./path/to.db`；`connect()` 里改为 `sqlite3.connect(cfg["file"])`。
- **Oracle / SQL Server**：同理，换驱动即可。

如果你需要支持多种数据库，可以在 ini 里加 `type = mysql`，然后在 `connect()` 里根据 `type` 分支。

## Q4: `对话文件夹/` 会越积越多，需要清理吗？ {#q4}

**不建议删**，但建议**归档**：

- 每月或每季度，把超过 N 个月没动过的对话目录打包成 zip，放到项目外的归档目录。
- 真正要删的，是那些「跑了一次就失败、没产出、说明也没填」的目录。

`对话文件夹/` 的价值就在于**可追溯**；删掉等于丢掉了「上次是怎么做的」这件事。

## Q5: `1配置文件/` 下的密码是明文，安全吗？ {#q5}

这是一个真实顾虑。建议：

1. **本地开发**：明文 ini + `.gitignore` 排除，是合理选择。
2. **团队共享 / 服务器**：考虑把密码移到环境变量，ini 里只写非敏感字段。`config_loader.py` 可以扩展为「先查环境变量，找不到再读 ini」。
3. **生产环境**：通常不该用这个模式 —— 生产 DB 连接应该走应用自身的配置体系，这个模式是**给数据处理 / 取数 / 对账**这种旁路任务用的。

## Q6: 这个模式适合长期运行的定时任务吗？ {#q6}

**不太适合。** 这个模式是**给一次性 / 几次性的数据处理任务**设计的。

如果你要做：
- 每天定时同步数据 → 用 APScheduler / Celery / Airflow，把脚本沉到 `工具/` 或独立目录，不要每次开新对话目录。
- 长期运行的服务 → 走正常的项目结构，不要用本模式。

如果只是「每周手动跑一次对账」，仍然适用：每周开一个新对话目录。

---

## Q7: 任务跨多个项目时，应该放哪个项目的 `对话文件夹/`？ {#q7}

放在**「主导方」项目**里。

判断主导方：
- 哪个项目**拥有最终交付物**（报告、修复后的数据）？
- 哪个项目的成员以后最常回来查这次记录？

把对话目录放在那个项目下，并在 `对话说明.md` 里明确说清「涉及了哪些其它项目」。

---

## Q8: 团队协作时，`对话文件夹/` 要不要进版本库？ {#q8}

**分情况**：

- **脚本是关键产物**（团队要复用 SQL / 处理逻辑）→ 把 `对话文件夹/*/脚本/` 加进版本库，但 `输出数据/` 通常太大不进。
- **对话目录只是个人工作记录** → 整个 `对话文件夹/` 加进 `.gitignore`，本地保留即可。

推荐做法：`.gitignore` 默认排除 `对话文件夹/*/`，但保留几个示例对话作为模板参考（用 `!` 例外）。

## Q9: 写操作前一定要备份吗？只改一行也要？ {#q9}

**一定要。** 理由有三个：

1. **改一行也可能改错**。`WHERE` 条件少写一个引号、多一个 OR，影响行数可能从 1 变成 10000。
2. **备份成本极低**。一行 `backup_table()` 就搞定，CSV 也只有几 KB。
3. **形成肌肉记忆**。如果"改少不备份、改多才备份"，迟早会因为判断失误翻车。一律备份，不用思考。

**唯一可以不备份的情况**：明确知道目标表是临时表 / 测试表，而且**随时可以从源头重建**。这种情况建议在 `对话说明.md` 里写清楚"为何不备份"。

## Q10: 备份 CSV 已经生成了，怎么回滚？ {#q10}

`工具/db_backup.py` 在备份的同时会生成一份 `备份/<表名>_rollback.sql`，里面是 `REPLACE INTO` 语句，依赖原表的主键 / 唯一索引做幂等覆盖。

回滚步骤：

```bash
# 1. 找到回滚 SQL（在本次对话目录的 备份/ 下）
ls 对话文件夹/<某次任务>/备份/

# 2. 执行回滚（MySQL 示例）
mysql -h <host> -u <user> -p <database> < 对话文件夹/<某次任务>/备份/<表名>_rollback.sql

# 3. 验证（行数应该和备份时一致）
mysql -h <host> -u <user> -p <database> -e "SELECT COUNT(*) FROM <表名> WHERE <原修改条件>"
```

**注意**：`REPLACE INTO` 依赖原表有主键 / 唯一索引。如果原表没有，回滚 SQL 会产生重复行，需要先 `TRUNCATE` 目标范围再执行。

## Q11: dry-run 模式下能做什么，不能做什么？ {#q11}

**dry-run 可以做**：
- `SELECT` 任何数据
- `SELECT COUNT(*)` 统计影响行数
- `EXPLAIN` 查看 SQL 执行计划
- 生成备份 CSV（只读操作，不修改库）
- 生成回滚 SQL 文件

**dry-run 不能做**：
- `UPDATE` / `DELETE` / `INSERT INTO ... SELECT`
- `ALTER TABLE` / `TRUNCATE` / `DROP`
- `CREATE TABLE`（除非是临时表）
- `conn.commit()` 提交事务（dry-run 模式下应该不开启事务，或者直接 rollback）

判断标准很简单：**dry-run 模式下数据库里的数据不能有任何变化**。

## Q12: 批量更新（几百万行）也走这个流程吗？ {#q12}

**流程一样，但策略要调整**：

1. **备份仍然必须**。但几百万行的 CSV 会很大（可能几个 GB），建议：
   - 只备份**主键 + 要修改的列**，不要 `SELECT *`
   - 或者分批备份，每批 10 万行一个 CSV
2. **dry-run 仍然必须**。`SELECT COUNT(*)` 在几百万行上可能要几秒，耐心等。
3. **执行要分批**。不要一次性 `UPDATE` 几百万行，会锁表很久。用 `LIMIT` 分批：
   ```sql
   UPDATE <表> SET ... WHERE ... LIMIT 10000;
   -- 重复执行直到 affected_rows = 0
   ```
4. **回滚也要分批**。`REPLACE INTO` 批量插入，每批 500-1000 行比较合适。

具体操作可以参考 `工具/db_backup.py` 里的 `batch_size` 参数。
